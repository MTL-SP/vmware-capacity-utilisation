// the point of all this

vCenter shows now. We needed over time.

vCenter is great at telling you a cluster is 82% full right this second. It's hopeless at telling you it was 60% a month ago and climbing. So we snapshot capacity every night and keep the history — now "is this thing filling up?" is a chart, not a guess.

📈 Capacity planning

Spot a cluster trending toward full before it actually is.

🔎 Incident context

"Was this datastore already at 95% last week?" Now you can answer.

📊 Reporting

Historical % usage for management, without manual screenshots.

It runs on a schedule, so most of your job is monitoring & troubleshooting — not babysitting. The whole point is that it's boring when it's healthy.

Six bits of tech, one job each

Tap a card to find out what it actually does for us.

tap ⊕

PowerShell 7

runs the show

Microsoft's modern scripting shell. Our collector is a single .ps1 script it executes.

Cross-platform, so the same script runs on Linux or Windows. No clicking required — it's built to run unattended.
tap ⊕

VMware PowerCLI

talks to vCenter

A PowerShell module full of VMware commands. Think "the vCenter API, in PowerShell."

Logs in read-only and pulls host/cluster/datastore data via commands like Connect-VIServer and Get-Cluster. Either VMware.PowerCLI or VCF.PowerCLI works.
tap ⊕

PostgreSQL

remembers everything

The database. Every snapshot lives here as rows in tables; we read it back with SQL.

Five tables in total — one audit log plus four metric tables (host, cluster, cluster-HA, datastore).
tap ⊕

TimescaleDB

time-travel mode

A Postgres add-on that makes time-stamped data fast — and tidies up after itself.

Two automatic chores: retention deletes data older than 24 months, compression squashes data older than 30 days. You don't touch these.
tap ⊕

Grafana

draws the charts

The dashboard tool. It reads from Postgres and visualises trends — strictly read-only.

Grafana never changes the data. If a chart looks wrong, the data is probably fine — check filters and time range first.
tap ⊕

psql

the delivery van

Postgres' command-line client. It's how the script actually writes rows into the database.

Must be installed and on the PATH of the machine running the collector — a classic cause of "it won't write" failures.

// what one run looks like

Six steps, one transaction

Every execution gets a unique run_id and is recorded in the audit table. Either the whole snapshot lands, or the run is marked failed — never anything half-written.

STEP 1 → 3

Wake up & collect

Load config & validate → mark a new run running → connect to vCenter and walk every cluster, host and datastore, doing the capacity maths in memory.

STEP 4 → 6

Write & sign off

Write everything in one transaction → mark the run success with row counts. If anything trips, it's marked failed with a sanitised error message.

The capacity_collection_runs table is your morning coffee check. One row per run, with status and row counts. success = sleep well.

Setup & configuration tutorial

Here's the good news: this is a one-time job, and the test lab is already wired up. But you should know how it all came together — so if it ever needs rebuilding, you're not starting from a blank stare.

Six things need to be in place before the collector can do anything useful.

PowerShell 7+

The shell that runs the collector script.

VMware PowerCLI

Either VMware.PowerCLI or VCF.PowerCLI installed.

Get-Module -ListAvailable

PostgreSQL + TimescaleDB

A running Postgres with the Timescale extension available.

CREATE EXTENSION timescaledb

psql on the PATH

The CLI the script writes rows through. Must be callable.

psql --version

vCenter read-only account

A least-privilege service account — read is all it needs.

svc-vcenter-readonly

A Postgres app user

Can create tables and insert data into the target DB.

vmware_collector

02 Wiring up the database

Six steps, top to bottom. Copy each block as you go.

1

Create the database

As a Postgres admin, make a home for the data.

psql · as admin
CREATE DATABASE vmware_capacity;
2

Create the app user

The collector logs in as this account. Restrict privileges further if your org requires it.

psql · as admin
CREATE USER vmware_collector WITH PASSWORD 'replace_me';
GRANT ALL PRIVILEGES ON DATABASE vmware_capacity TO vmware_collector;
3

Enable TimescaleDB

Connected to the target DB, switch on the time-series superpowers. (If extensions are locked down, your DBA does this once.)

psql · in vmware_capacity
CREATE EXTENSION IF NOT EXISTS timescaledb;
4

Create the secret files

Passwords live in files, never in config. One for the DB, one for vCenter — value only, locked down tight.

bash
mkdir -p /opt/vmware-capacity/secrets
printf '%s' 'pg_password' > /opt/vmware-capacity/secrets/pg_password.txt
printf '%s' 'vc_password' > /opt/vmware-capacity/secrets/vc_password.txt
chmod 600 /opt/vmware-capacity/secrets/*.txt
powershell
New-Item -ItemType Directory -Force C:\vmware-capacity\secrets
Set-Content -NoNewline C:\vmware-capacity\secrets\pg_password.txt 'pg_password'
Set-Content -NoNewline C:\vmware-capacity\secrets\vc_password.txt 'vc_password'
# then restrict the folder to the run account with icacls
5

Initialize the schema

Run the bootstrap script once. It creates every table, hypertable, index, and the retention & compression policies.

pwsh · one-time
pwsh ./scripts/init-db.ps1 `
  -PGHost db.example.local -PGPort 5432 `
  -PGDatabase vmware_capacity `
  -PGUsername vmware_collector `
  -PGPasswordFile /opt/vmware-capacity/secrets/pg_password.txt
6

Create the collector config

Copy collector-config.sample.psd1 and fill in your details. Notice the passwords are just paths — the values stay in the secret files.

collector-config.psd1
@{
    VCServer       = "vcenter.example.local"
    VCUsername     = "svc-vcenter-readonly"
    VCPasswordFile = "/opt/vmware-capacity/secrets/vc_password.txt"

    PGHost         = "db.example.local"
    PGPort         = 5432
    PGDatabase     = "vmware_capacity"
    PGUsername     = "vmware_collector"
    PGPasswordFile = "/opt/vmware-capacity/secrets/pg_password.txt"

    VCenterName    = "Production-vCenter"   # optional friendly name
    BatchingThresholdRows = 10000           # advisory warning threshold
}
7

Schedule the nightly run

This is what makes it daily. Point your scheduler at capacityutilization.ps1 — the one-time init-db.ps1 is never scheduled.

crontab -e · runs 01:00 daily
# m h dom mon dow   command
0 1 * * * /usr/bin/pwsh /opt/vmware-capacity/capacityutilization.ps1 `
  -ConfigFile /opt/vmware-capacity/collector-config.psd1 `
  >> /var/log/vmware-capacity.log 2>&1
powershell · register a daily task
$action = New-ScheduledTaskAction -Execute "pwsh.exe" `
  -Argument "-File C:\vmware-capacity\capacityutilization.ps1 -ConfigFile C:\vmware-capacity\collector-config.psd1"
$trigger = New-ScheduledTaskTrigger -Daily -At 1:00AM
Register-ScheduledTask -TaskName "VMware Capacity Collector" `
  -Action $action -Trigger $trigger -RunLevel Highest -User "SYSTEM"
Step 5 is safe to re-run — everything uses IF NOT EXISTS. But treat it as change-managed, not a daily chore. The nightly job only ever runs capacityutilization.ps1.

03 Sneak peek: the database schema

Five tables: one audit log plus four metric tables. Click through to see the columns — green = primary key.

The four metric tables are hypertables on snapshot_ts_utc — they auto-compress after 30 days and auto-delete after 24 months. Those composite primary keys are what make re-running a snapshot safe: same keys → no duplicates.

Troubleshooting, decoded

Always start the same way: check the run status, read the error_message, match it below. Click a row to reveal the fix.

Secret file not found The script can't find a password file
Usually a path that moved or a typo.
Check the VCPasswordFile / PGPasswordFile paths in collector-config.psd1. The file should contain only the password.
PowerCLI not installed "PowerCLI module is not installed."
The host is missing the VMware module.
Install VMware.PowerCLI or VCF.PowerCLI on the machine running the collector.
vCenter login failed Connect-VIServer can't get in
Bad service-account creds, or vCenter is unreachable.
Verify the read-only service account and that vCenter is reachable from the host. If the password changed, update the secret file.
psql command failed The database write didn't go through
DB unreachable, wrong DB creds, or psql isn't on the PATH.
Test DB connectivity and confirm psql is installed and on the PATH. Then just re-run.
stuck on “running” An old run never finished
The process was killed mid-run.
Just re-run it. The single-transaction design means there's no half-written data to clean up. Re-running is always safe (it's idempotent).
no new run at all Nothing showed up this morning
If there's no new row in capacity_collection_runs, the collector never started.
Suspect the scheduler first — cron (Linux) or Task Scheduler (Windows). The script can't fail if it never ran.
dashboard empty Grafana says "No data"
Often the time range is too narrow, or the datasource is off.
Widen the time range and confirm Grafana's PostgreSQL datasource is healthy. Remember the data is real only after a successful run.

Copy-paste cheat sheet

The four things you'll actually run. Hit copy.

run it manually
pwsh ./capacityutilization.ps1 `
  -ConfigFile collector-config.psd1 `
  -ShowConsoleSummary
did last night work?
SELECT run_id, status, started_at_utc,
       host_rows, cluster_rows, datastore_rows
FROM capacity_collection_runs
ORDER BY started_at_utc DESC LIMIT 10;
why did it fail?
SELECT status, error_message, started_at_utc
FROM capacity_collection_runs
WHERE status = 'failed'
ORDER BY started_at_utc DESC LIMIT 5;
is there any data?
SELECT count(*) FROM host_capacity_metrics;
SELECT count(*) FROM cluster_capacity_metrics;
SELECT count(*) FROM datastore_capacity_metrics;
